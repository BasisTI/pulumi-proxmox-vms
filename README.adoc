= pulumi-proxmox-vms

This repository contains a Pulumi component for quickly creating and managing Proxmox VE virtual machines from a Linux template using cloud-init.

== Features

* Create multiple VMs by cloning a Proxmox template
* Automatic network configuration with static IP addresses via cloud-init
* Configurable CPU cores, CPU type, memory, and disk settings per VM
* Optional per-VM `role` (e.g. `master`, `worker`) recorded as a Proxmox tag
* Tag-based VM grouping (replaces vSphere folder structure)
* QEMU guest agent support
* HA migration drift protection via `IgnoreChanges` on `nodeName`
* Easy configuration through Pulumi YAML files

== Installation

Add this component to your Go project:

[source,bash]
----
go get github.com/BasisTI/pulumi-proxmox-vms
----

== Usage

=== Basic Usage

The component provides two ways to create VMs:

1. **Automatic configuration reading** (recommended):
+
[source,go]
----
import (
    "github.com/BasisTI/pulumi-proxmox-vms/proxmox-vms"
    "github.com/pulumi/pulumi/sdk/v3/go/pulumi"
)

func main() {
    pulumi.Run(func(ctx *pulumi.Context) error {
        // Create VMs using configuration from Pulumi YAML files
        proxmoxVms, err := proxmox_vms.NewProxmoxVmsFromConfig(ctx, "my-vms")
        if err != nil {
            return err
        }

        // Export VM IDs
        var vmIds []pulumi.StringOutput
        for _, vm := range proxmoxVms.VirtualMachines {
            vmIds = append(vmIds, vm.ID().ToStringOutput())
        }
        ctx.Export("vmIds", pulumi.ToStringArrayOutput(vmIds))
        return nil
    })
}
----

2. **Manual configuration**:
+
[source,go]
----
args := &proxmox_vms.ProxmoxVmsArgs{
    Vms:        []proxmox_vms.VmData{...},
    ProxmoxCfg: proxmox_vms.ProxmoxCfg{...},
    NetworkCfg: proxmox_vms.NetworkCfg{...},
}
proxmoxVms, err := proxmox_vms.NewProxmoxVms(ctx, "my-vms", args)
----

== Configuration

When using `NewProxmoxVmsFromConfig`, the component automatically reads three required configuration objects and one optional parameter from your Pulumi YAML files:

=== Optional Configuration Parameters

==== `makeAlias` - Resource Aliasing

[source,yaml]
----
makeAlias: true
----

.MakeAlias Parameter
[cols="1,1,3"]
|===
|Field |Type |Description

|`makeAlias`
|bool
|Optional. When set to `true`, creates Pulumi resource aliases for existing VMs. This is useful when refactoring existing projects to use this component, allowing Pulumi to recognize existing resources instead of trying to recreate them. Defaults to `false` if not specified.
|===

=== Required Configuration Objects

==== `vms` - Virtual Machines Configuration

Array of VM specifications:

[source,yaml]
----
vms:
  - name: "k8s-master-01"
    hostName: "k8s-master-01"
    ipv4address: "192.168.24.32"
    numCpus: 4
    memory: 8192
    role: master
  - name: "k8s-worker-01"
    hostName: "k8s-worker-01"
    ipv4address: "192.168.24.33"
    numCpus: 2
    memory: 4096
    role: worker
    cpuType: x86-64-v3
----

.VM Configuration Fields
[cols="1,1,3"]
|===
|Field |Type |Description

|`name`
|string
|Name of the virtual machine in Proxmox

|`hostName`
|string
|Hostname to be set via cloud-init

|`ipv4address`
|string
|Static IPv4 address for the VM

|`numCpus`
|int
|Number of CPU cores

|`memory`
|int
|Memory size in MB

|`role`
|string
|Optional. Role of the VM in its group (e.g. `master`, `worker`). Added to the VM tags in Proxmox, next to `proxmoxCfg.tags`, so the role is visible in the UI and queryable by the API. Empty means no extra tag.

|`cpuType`
|string
|Optional. CPU type for this VM (e.g. `x86-64-v3`, `host`). Overrides `proxmoxCfg.cpuType`. Changing the type of a running VM takes effect on its next restart.
|===

==== `proxmoxCfg` - Proxmox Environment Configuration

[source,yaml]
----
proxmoxCfg:
  nodeName: pve1
  datastoreId: local-lvm
  templateVmId: 9000
  diskSize: 50
  tags:
    - Production
    - Kubernetes
  onBoot: true
  agent: true
  cpuType: x86-64-v3
  rebootAfterUpdate: false
----

.Proxmox Configuration Fields
[cols="1,1,3"]
|===
|Field |Type |Description

|`nodeName`
|string
|Proxmox node where **new** VMs are created. Existing VMs are located by name on any node of the cluster at every run (see <<node-discovery>>), so a VM migrated in Proxmox keeps being managed without touching this value.

|`datastoreId`
|string
|Storage ID for VM disks (e.g., "local-lvm")

|`templateVmId`
|int
|VM ID of the template to clone from

|`diskSize`
|int
|Disk size in GB for each VM

|`tags`
|[]string
|Tags for VM grouping (replaces vSphere folders)

|`onBoot`
|bool
|Start VM automatically on host boot

|`agent`
|bool
|Enable QEMU guest agent

|`cpuType`
|string
|Optional. Default CPU type for every VM (e.g. `x86-64-v3`). A VM can override it with its own `cpuType`. When neither is set the type is not sent and the provider default (`qemu64`) applies, which keeps existing stacks unchanged.

|`rebootAfterUpdate`
|bool
|Optional, defaults to `false`. When `true` the provider reboots a VM right after an update that needs one (CPU type, memory), and `pulumi up` updates the VMs in parallel, so a whole cluster can restart at once. Leave it `false` and restart the VMs one at a time; the pending change is applied on that restart. The component always sends the value, because the provider default is `true`.
|===

==== `networkCfg` - Network Configuration

[source,yaml]
----
networkCfg:
  gateway: 192.168.24.1
  dnsServers:
    - 192.168.24.5
  domain: example.com
  mask: 23
  bridge: vmbr0
----

.Network Configuration Fields
[cols="1,1,3"]
|===
|Field |Type |Description

|`gateway`
|string
|Network gateway IP address

|`dnsServers`
|[]string
|List of DNS server IP addresses

|`domain`
|string
|Network domain name

|`mask`
|int
|Subnet mask in CIDR notation (e.g., 24 for /24)

|`bridge`
|string
|Proxmox network bridge (default: "vmbr0")

|`model`
|string
|NIC model (default: "virtio")

|`vlanTag`
|int
|Optional VLAN tag
|===

[[node-discovery]]
== Node discovery and migrated VMs

The provider addresses a VM by `nodeName` + id. Its **read** path (`pulumi refresh`) looks the
VM up by id in `GET /cluster/resources` and rewrites `nodeName` in the state, so a VM migrated
in Proxmox is found again. Its **update** path does not: it uses the node stored in the state,
and a VM migrated after the last refresh makes `pulumi up` fail with
`error retrieving VM <id>: the requested resource does not exist`.

Since v2.3.0 the component also lists the VMs of the cluster (`getVirtualMachines`) on every
run, matches each configured VM by name (templates are skipped, duplicate names are an error)
and passes the node Proxmox reports. `proxmoxCfg.nodeName` is only used to create VMs that do
not exist yet. The VM resources are created with `migrate: true`, so a node change is never
planned as a replace: when the state is stale the update fails instead of re-creating the VM.

**After a VM is migrated in Proxmox**, refresh before applying:

[source,bash]
----
pulumi refresh          # or: pulumi up --refresh
pulumi preview          # no nodeName diff expected any more
----

A preview showing `nodeName: <old> => <real>` means the state was not refreshed since the
migration. Refresh; do not apply.

== Migrating from vSphere

This component is designed as a drop-in replacement for `pulumi-vsphere-vms`. Key differences:

* **Folders -> Tags**: Replace `vmsFolder` with `tags` array
* **Template by name -> Template by VM ID**: Replace `templateName`/`templateFolder` with `templateVmId`
* **Guest customization -> Cloud-init**: Network configuration is applied via cloud-init instead of vSphere guest customization
* **Cluster -> Node**: Replace `cluster` with `nodeName` (explicit node placement)
* **Config key**: Replace `vsphereCfg` with `proxmoxCfg` in your Pulumi YAML files

== Prerequisites

* Proxmox VE environment with API access
* Linux VM template with cloud-init configured
* Pulumi CLI installed and configured
* Go 1.24 or later

== Template Requirements

Your Linux template should be configured with:

* Cloud-init package installed and enabled
* QEMU guest agent installed (if using `agent: true`)
* Network configuration set to use cloud-init
* A unique VM ID that will be referenced in `templateVmId`
